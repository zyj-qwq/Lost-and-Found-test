# 03 · 核心流程图解（登录 → 发布 → 审核 → 认领）

> 这篇用"一步步跟踪数据"的方式，讲清楚系统的四个核心流程。所有步骤都标注了对应的文件，可以边看代码边对照。

---

## 流程一：注册和登录（token 是什么）

**注册：**

```
用户填用户名/密码，点"注册"
  → LoginView.vue 的 handleRegister()
  → post('/auth/register', { username, password })
  → 后端 index.js：校验格式（正则）→ 分配 uid（计数器+1）
    → 密码用 bcrypt 加密后存入 db.json
  → 返回 { username, uid, role }
  → 前端弹提示"你的 uid 是 xxx，请牢记" → 自动切到登录页并填好 uid
```

**登录（关键：理解 token）：**

```
用户输入 uid + 密码，点"登录"
  → auth store 的 login() → post('/auth/login', { uid, password })
  → 后端：bcrypt 对比密码 → 正确则用 jwt.sign 签发一个 token（有效期7天）
  → 前端 setAuth()：token 存到 ①Pinia 内存 ②localStorage（两处都存！）
       内存：保证当前页面立刻生效
       localStorage：保证刷新页面/明天再打开还是登录状态
```

**token 之后的每一次请求：**

```
任何需要登录的接口
  → axios 请求拦截器（api/index.ts）自动执行：
    localStorage 取出 token → 塞进请求头 Authorization: Bearer xxx
  → 后端 auth 中间件：jwt.verify 校验 → 通过则把用户挂到 req.user → 放行
  → token 无效/过期 → 返回 code=10002
    → 响应拦截器：清 localStorage + 通知 store 清内存 + 弹提示 + 跳登录页
```

> **一句话**：token 就是"进场的临时通行证"。登录时发给你，之后每次进门出示一次。通行证过期就被门卫拦下赶回售票处（登录页）。

**防"假登录"（我们修过的 bug）：**

```
App.vue 挂载完成 → onMounted 调 auth.init()
  → 拿着本地存的 token 去调 GET /auth/me
  → 有效：刷新用户信息；无效：拦截器清理并跳登录页
```

## 流程二：发布信息（为什么要"审核"）

```
① PublishView.vue：用户填表单（v-model 实时存进 form 对象）
     图片那一步：el-upload 先把图片传给 POST /upload
       → 后端 multer 存文件（随机文件名，防安全问题）→ 返回图片网址
       → 前端把网址 push 进 form.images（表单里只存网址不存图片本身）

② 点"提交发布" → 校验必填项 → POST /items
     → 后端：再校验一遍 → 创建 item，status='pending'（待审核）
       关联 uid=req.user.uid（谁登录的就归谁）

③ 此刻去首页看：看不到这条信息！
     因为首页接口有规则：没指定 status 时只返回 approved 的

④ 管理员在后台审核 → 见流程三
```

> **为什么修改后要重新审核？** 防止有人先发正常内容骗过审核，再改成垃圾内容。所以 PUT 接口会把 status 重新置回 pending。

## 流程三：管理员审核

**信息审核（ItemReview.vue）：**

```
① 管理员登录（role=item_admin 或 system_admin）
     登录后 auth.isAdmin 为 true → 导航栏自动出现"管理后台"入口
     （没登录/普通用户直接输网址 /admin？路由守卫 beforeEach 会拦下）

② 打开 /admin/items → GET /admin/items?status=pending
     → 后端 requireRole 中间件检查角色 → 不对就返回 10003 没有权限

③ 点"通过" → 弹窗(prompt)填备注 → PUT /admin/items/3 { status:'approved', remark }
     → 后端更新该条记录的 status → save() 写入 db.json
     → 首页立刻能看到了（因为下次查询时它满足 approved 条件）
```

**认领审核（ClaimReview.vue）—— 多了一步"联动"：**

```
管理员通过某条认领申请（PUT /admin/claims/1 { status:'approved' }）
  → 后端做三件事：
    ① 这条申请 → approved
    ② 对应的物品 → claimed（已认领）
    ③ 同一物品的其他 pending 申请 → 全部自动 rejected，备注"该物品已被他人认领"
```

> 这三件事在一个接口里完成，是"业务联动"的典型例子：改 A 的时候，和 A 相关的 B、C 也要同步改，否则数据就矛盾了（东西被一个人领了，别人的申请还挂着"待审核"就很奇怪）。

## 流程四：申请认领

```
① 用户打开详情页 /items/3
     ItemDetailView 用 route.params.id 拿到 "3" → GET /items/3 → 显示详情

② 显示什么按钮由"状态 + 身份"决定（v-if 组合）：
     status=approved 且 不是发布人  → 显示"申请认领"按钮
     status=pending                → 显示"等待审核"提示条
     status=claimed                → 显示"已完成认领"
     我是发布人                    → 显示 编辑/删除 按钮
     （isOwner 是 computed：item 或 auth.user 变了它自动重算）

③ 填证明 → POST /items/3/claims
     → 后端四道检查：
       ① 物品存在？② 不是自己的？③ 状态是 approved？④ 没有 pending 的重复申请？
       → 都通过才创建申请

④ 用户在"我的申请"页能看到进度（GET /me/claims）
     通过 → 状态"已通过"；驳回 → "已驳回"+ 管理员的备注原因
```

## 三种角色的权限地图

| 功能 | 游客 | 普通用户 | 招领管理员 | 系统管理员 |
|---|:-:|:-:|:-:|:-:|
| 浏览信息 / 公告 | ✅ | ✅ | ✅ | ✅ |
| 注册 / 登录 | ✅ | ✅ | ✅ | ✅ |
| 发布 / 编辑 / 删除自己的信息 | ❌ | ✅ | ✅ | ✅ |
| 申请认领 | ❌ | ✅ | ✅ | ✅ |
| 查看自己的发布 / 申请 | ❌ | ✅ | ✅ | ✅ |
| 信息审核 / 认领审核 / 数据统计 | ❌ | ❌ | ✅ | ✅ |
| 用户管理（改角色/禁用） | ❌ | ❌ | ❌ | ✅ |
| 公告管理 | ❌ | ❌ | ❌ | ✅ |

前端用**两层防护**实现：
1. **界面层**：`v-if="auth.isLoggedIn"`、`v-if="auth.isAdmin"` 控制入口显示/隐藏；
2. **路由层**：`router/index.ts` 的 beforeEach 守卫检查 meta 权限标记。

⚠️ 但这两层都可能被绕过（直接用工具发请求）。所以**后端必须再防一层**：`auth` 中间件 + `requireRole` 中间件。这就是"前端防君子，后端防小人"。

## 数据长什么样（db.json 节选）

```jsonc
{
  "counters": { "uid": 10002, "itemId": 3 },   // 编号计数器
  "users": [
    { "uid": 10000, "username": "admin", "password": "$2a$10$...", "role": "system_admin" },
    { "uid": 10001, "username": "张小明", "password": "$2a$10$...", "role": "user" }
  ],
  "items": [
    {
      "id": 3, "type": "lost", "title": "黑色钱包",
      "status": "approved",        // pending→approved→claimed 的生命周期
      "uid": 10001,                // 谁发布的（和 users 表关联）
      "images": ["http://localhost:8080/uploads/xxx.jpg"]
    }
  ],
  "claims": [
    { "id": 1, "item_id": 3, "uid": 10002, "status": "pending", "proof": "..." }
  ],
  "announcements": [ ... ]
}
```

可以发现：表和表之间靠 **id 互相引用**（item.uid → users 表；claim.item_id → items 表）。这就是最朴素的关系型数据库思想，MySQL 里也一样，只是 MySQL 用 SQL 语句查询而我们直接操作 JS 数组（`filter`/`find`/`sort` 你都会）。
